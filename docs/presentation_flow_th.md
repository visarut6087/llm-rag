# สรุป Flow และสคริปต์พรีเซนต์: Baseline เทียบกับ RAG

เอกสารนี้สรุปจากโค้ดและผลทดลองที่มีอยู่ใน repository ณ วันที่ 8 ตุลาคม 2026 ใช้พูดประกอบสไลด์หรือสาธิตระบบได้

## เป้าหมายการทดลอง

เปรียบเทียบวิธีตอบคำถามภาษาไทยจากชุดคำถาม 50 ข้อเกี่ยวกับระเบียบงานสารบรรณ:

1. **Baseline ไม่ใช้ RAG:** ส่งคำถามตรงให้โมเดล Qwen2.5 7B ตอบด้วยความรู้ที่อยู่ในโมเดล ไม่มีการค้นคลังเอกสาร
2. **โมเดลเล็กใช้ RAG:** ค้นหลักฐานจากคลังเอกสารก่อน แล้วส่งคำถามพร้อมหลักฐานให้ Gemma 3 4B สร้างคำตอบ พร้อมแหล่งอ้างอิง

## Flow ของผู้ใช้ตั้งแต่ต้นจนจบ

### เตรียมคลังความรู้ (ทำครั้งแรกหรือเมื่อมีเอกสารใหม่)

```text
ไฟล์เอกสารใน backend/dataset
  → อ่านไฟล์ข้อความและแบ่งตามย่อหน้า (คั่นด้วยบรรทัดว่าง)
  → สร้างเวกเตอร์ด้วย text embedder
  → บันทึกข้อความ เวกเตอร์ ชื่อแหล่ง และ chunk ID ลง ChromaDB
```

ระบบมี collection สำหรับข้อความและรูปภาพแยกกัน ส่วนการทดลองชุดนี้เป็นคำถามจากเอกสารข้อความ `sarabun 26.txt` โดยใช้คลัง ChromaDB ที่เตรียมไว้

### A. Baseline ไม่ใช้ RAG

```text
ไฟล์คำถาม 50 ข้อ + คำตอบอ้างอิง
  → evaluate_llm_baseline.py อ่าน dataset
  → ส่งคำถามตรงไป Ollama /api/chat (Qwen2.5 7B, temperature 0)
  → รับคำตอบและเวลา/token จาก Ollama
  → บันทึก JSON และ CSV
```

ไม่มีการเรียก API ค้น RAG และไม่มีหลักฐานจากเอกสารใน prompt ของโมเดลตามที่กำหนดในสคริปต์ baseline ผลแต่ละแถวบันทึก `rag_used: false`

### B. โมเดลเล็กใช้ RAG

```text
ไฟล์คำถาม 50 ข้อ
  → evaluation runner ส่งคำถามไป FastAPI /api/rag/query
  → (ถ้าเปิดใช้) ปรับ query สำหรับคำถามต่อเนื่อง
  → embed คำถามและค้น chunk ใกล้เคียงจาก ChromaDB
  → กรองหลักฐานข้อความที่ว่างหรือ cosine distance เกินเกณฑ์
  → สร้าง context พร้อม source/chunk/citation ID [S1]...
  → runner ส่งคำถาม + context ไป Ollama /api/chat (Gemma 3 4B)
  → บันทึกคำตอบ หลักฐาน citation เวลา/token ลง JSON และ CSV
```

การค้นคืนปัจจุบันใช้ cosine distance จาก ChromaDB ซึ่ง **ค่ายิ่งต่ำยิ่งใกล้**; เกณฑ์หลักฐานเริ่มต้นคือ `0.22` และ top-k ในผลรันคือ 3. หากมีหลักฐานไม่พอ prompt กำหนดให้โมเดลแจ้งว่าไม่พบข้อมูลเพียงพอ ประวัติสนทนา (ถ้าส่งมา) ใช้ช่วยตีความคำถาม ไม่ถือเป็นหลักฐานข้อเท็จจริง

ใน API มีตัวเลือก query rewriting, citations และ reranker แต่ในผลชุดที่เลือกนี้ runner ตั้ง `n_results=3`; การเปิดใช้ reranker ไม่ได้ถูกระบุในพารามิเตอร์ผลรัน จึงไม่ควรกล่าวว่าผลนี้ผ่าน reranking ส่วนหน้าเว็บมีสวิตช์ RAG แยก และเมื่อเปิดจะดึง context จาก FastAPI ก่อนส่งบทสนทนาให้ Ollama

## ผลการรันที่มีอยู่

| รายการ | Baseline ไม่ใช้ RAG | โมเดลเล็กใช้ RAG |
|---|---:|---:|
| โมเดล | `qwen2.5:7b` | `gemma3:4b` |
| คำถามที่ขอ | 50 | 50 |
| ตอบสำเร็จ / error | 50 / 0 | 50 / 0 |
| RAG | ปิด | เปิด, top-k 3 |
| เวลาเฉลี่ยต่อข้อจากไฟล์ผล | 5.40 วินาที | 6.59 วินาที |
| มี source/citation ในผล | ไม่มี | มี; แถวผลทั้ง 50 มี sources และ citation field |
| ผลลัพธ์ | `results/baseline_no_rag/qwen2.5_7b/answers_20261008_145516.json` และ CSV คู่กัน | `results/sarabun-questions50__gemma3_4b__default__20261006_183352/answers.json` และ CSV คู่กัน |

เวลาเฉลี่ยคำนวณจาก `latency_ms` ที่บันทึกในแต่ละแถว ปัดทศนิยมสองตำแหน่ง (5,398.5 และ 6,590.9 ms ตามลำดับ) เป็นเวลา end-to-end ที่ runner วัดไว้ จึงรวมค่าใช้จ่ายของการค้น RAG ในรันที่สองด้วย

## สคริปต์พูดประกอบการนำเสนอ

### เปิดเรื่อง

“งานนี้ศึกษาว่าการดึงเอกสารมาเป็นหลักฐานก่อนตอบ ช่วยให้โมเดลตอบคำถามจากเอกสารภาษาไทยได้ตรวจสอบย้อนกลับได้อย่างไร เราเตรียมชุดคำถามเกี่ยวกับระเบียบงานสารบรรณจำนวน 50 ข้อ แล้วทดลองสองแนวทาง คือ baseline ที่ถามโมเดลโดยตรง กับ RAG ที่ค้นเอกสารก่อนตอบ”

### อธิบาย Baseline

“ฝั่ง baseline สคริปต์อ่านคำถามทีละข้อ แล้วส่งตรงให้ Qwen2.5 7B ผ่าน Ollama โดยไม่ค้นคลังเอกสารและไม่แนบ context ระบบเก็บคำตอบ เวลา และจำนวน token ไว้เทียบภายหลัง การทดลองนี้ได้คำตอบครบ 50 ข้อ ไม่มี error”

### อธิบาย RAG

“ฝั่ง RAG เอกสารต้นทางถูกแบ่งเป็น chunk ตามย่อหน้า แปลงเป็นเวกเตอร์และเก็บใน ChromaDB เมื่อได้คำถาม ระบบแปลงคำถามเป็นเวกเตอร์ แล้วค้น chunk ที่ใกล้ที่สุดสามรายการ จากนั้นตรวจว่าเนื้อหามีอยู่และคะแนนระยะห่างผ่านเกณฑ์หรือไม่ จึงประกอบหลักฐานพร้อมรหัสแหล่ง เช่น S1 ส่งให้ Gemma 3 4B ตอบ โดยกำชับให้อิงหลักฐานและระบุเมื่อหลักฐานไม่พอ ผลรันที่เลือกได้คำตอบครบ 50 ข้อ และเก็บ sources/citations ไว้ตรวจสอบ”

### สาธิต end to end

“ผมจะเลือกคำถามหนึ่งข้อจากชุดทดสอบให้ดู ก่อนอื่นดูคำตอบ baseline ซึ่งเกิดจากความรู้ในโมเดล จากนั้นดูคำตอบ RAG พร้อม chunk ที่ค้นได้และ citation แล้วเทียบกับคำตอบอ้างอิงของ dataset จุดสำคัญคือเราตรวจได้ว่าคำตอบ RAG ใช้หลักฐานส่วนใด ไม่ได้ดูเฉพาะข้อความคำตอบอย่างเดียว”

### สรุปผลและข้อจำกัด

“ในผลที่บันทึกไว้ baseline ใช้เวลาเฉลี่ยประมาณ 5.40 วินาทีต่อข้อ ส่วน RAG ใช้ประมาณ 6.59 วินาทีต่อข้อ ซึ่งรวมเวลาค้นหลักฐานและสร้างคำตอบ ทั้งสองชุดทำงานครบ 50 ข้อ อย่างไรก็ตาม สองรันนี้ใช้คนละโมเดล คือ Qwen2.5 7B กับ Gemma 3 4B และยังไม่มีคะแนนประเมินคุณภาพคำตอบหรือ hallucination ที่มนุษย์ตรวจยืนยัน ดังนั้นตัวเลขนี้ยืนยันจำนวนงานที่สำเร็จ เวลา และการมีหลักฐานประกอบได้ แต่ยังสรุปไม่ได้ว่า RAG ลด hallucination หรือคุณภาพคำตอบดีกว่า”

## ข้อควรพูดให้แม่นยำ

- พูดว่า “เปรียบเทียบผลการรันสองแนวทาง” ได้ แต่ไม่ควรอ้างว่า RAG เป็นสาเหตุเดียวที่ทำให้คุณภาพเปลี่ยน เพราะใช้คนละโมเดล
- การมี citation/source field ไม่ได้แปลว่า citation ถูกต้องหรือทุกข้อความมีหลักฐานรองรับ ต้องตรวจเทียบกับ chunk และคำตอบจริง
- ชุดคำถามมี expected answer แต่ไฟล์ผลยังไม่ได้บันทึกคะแนน correctness, faithfulness หรือ hallucination ที่ผ่านการให้คะแนน
- หากต้องการสรุปผลเชิงเหตุและผล ให้รันโมเดลเดียวกันกับ dataset, prompt, temperature และการตั้งค่าเดียวกัน โดยสลับเฉพาะ RAG off/on แล้วตรวจคำตอบด้วยเกณฑ์เดียวกัน

- ที่เก็บ vector และ cosine distance: `backend/db.py`
- Runner ที่เรียก RAG ก่อน Ollama: `scripts/evaluate_llm_nodb.py` หรือ `scripts/evaluate_llm_pc.py`
- ผล baseline: `results/baseline_no_rag/qwen2.5_7b/answers_20261008_145516.json`
